# 评审与证据

## 双线评审

不要用一份评审同时回答两类问题，它们的失败方式不同。

| 线 | 看什么 | 典型发现 |
| --- | --- | --- |
| A · 任务与视觉表达 | 用户能否理解、比较、行动；字体层级是否弱；真实内容是否不足；构图是否缺乏节奏；关键动作是否被淹没；品牌方向是否落到画面 | "平平无奇"被拆成可讨论的具体问题 |
| B · 操作与技术 | 键盘、焦点、响应式、状态覆盖、对比度、失败恢复、动效性能 | 功能通过但体验断裂 |

自己评自己的作品时，标注为"自查"，它不能自动充当独立验收。

## 问题卡格式

每条问题写四件事：

- **位置：** 哪个页面 / 区块 / 状态 / 视口
- **观察：** 实际看到或操作到什么
- **用户后果：** 对任务或理解造成什么影响
- **修复方向：** 建议怎么改

并标注级别：**必须修复**（影响任务完成、可访问性、误导）或 **审美建议**（可讨论、可不改）。两类分开列。

## 证据边界

- 截图证明可见状态。键盘操作、动画、失败恢复需要实际操作证据。
- 设计文档记录实现意图，不能替代原始需求；改文档不能消除未满足的用户目标。
- 功能通过与视觉、表达问题可以同时存在。token 一致、组件齐全、检测零报错都不等于设计优秀。
- 保存证据时标明版本、页面、视口、状态；修复后检查受影响部分，不用旧截图说明新版本。
- 没有目标用户参与，标"专家走查"。
- 外部仓库自带的盲评、自评分、性能描述属于作者材料，除非自己复现，否则不当作对你的项目有效的证明。

## 每轮迭代怎么控制

每轮集中修正最影响用户任务或视觉表达的少数几个问题。小改动不重新做定位、参考和整套系统。没有证据表明有进一步价值时就停。

## 最小交付清单

- [ ] 定位可说明：谁用、为什么选、有哪些真实证据
- [ ] 品牌可执行：每条原则对应具体界面行为，不只剩形容词
- [ ] 方向有差异：候选的结构、素材或叙事确实不同
- [ ] 页面有内容：真实信息可用；假想或样例内容已标记
- [ ] 操作有闭环：主动作、反馈、错误与恢复按实际需求覆盖
- [ ] 视觉有证据：保存当前版本代表性宽窄屏截图，说明页面与状态
- [ ] 结论有边界：区分视觉判断、功能检查、用户验证与未测试的假设
