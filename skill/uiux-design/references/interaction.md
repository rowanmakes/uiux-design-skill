# 交互、反馈与 UX

视觉决定第一眼，交互决定用户愿不愿意留下。本文件管"用户做一件事的整个过程"：从找到入口、操作、等待、看到结果，到出错和反悔。任何界面都适用；App、工作台、AI 的特有部分分别在 `app.md`、`workbench.md`、`ai.md`。

## 1. 先想清楚任务和流程

画界面之前，先用文字写出主任务的流程：

```
触发（用户为什么来）→ 第一步 → … → 完成（用户得到了什么）
```

- **每一步问三件事：** 这一步能不能省？能不能合并？能不能给个好的默认值？
- **先写顺利路径，再逐步问"如果这里出了问题"：** 网络断了、输入错了、没有数据、权限不够、用户中途离开又回来。
- **步骤用用户的话命名，** 不用系统内部术语。
- **高频操作走最短路径；低频高风险的操作可以多一步，但要明确。**
- 复杂功能逐层展开：默认只露出大多数人需要的，高级选项按需展开。

## 2. 一次交互的完整闭环

每个主要操作都要走完这五步，缺一步用户就会困惑：

| 阶段 | 用户想知道 | 界面要给 |
| --- | --- | --- |
| 1. 发现 | 我能在这里做什么？ | 看得出能点、能拖、能输入的样子；主操作最醒目 |
| 2. 操作 | 我按到了吗？ | 按下立刻有变化（按下态、选中态） |
| 3. 进行中 | 它在处理吗？要多久？ | 加载状态、进度、能取消 |
| 4. 结果 | 成功了吗？结果在哪？ | 结果本身出现在用户眼前；看不见的结果用一句话说出来 |
| 5. 下一步 | 接下来呢？做错了怎么办？ | 下一步的入口；撤销 |

**最好的反馈是结果本身当场发生**：点"加入收藏"，星星当场亮起并计数加一，而不是弹一个"操作成功"。只有结果看不见时（复制、后台保存、发送），才用一句提示说出结果本身，例如"已复制链接"。

## 3. 反馈：多快、放哪、说什么

**多快**（经典的响应时间界限）：

| 时间 | 用户的感受 | 要做的 |
| --- | --- | --- |
| 0.1 秒内 | 是我直接操作的 | 按下态、选中、开关切换必须在这个时间内 |
| 0.4 秒内 | 没有在等 | 超过就要先给出视觉回应（外框、骨架、进行中提示） |
| 1 秒内 | 思路没被打断 | 超过 1 秒显示加载状态 |
| 10 秒以上 | 注意力开始离开 | 显示进度和预计时间，允许转到后台、允许取消 |

骨架屏在 200ms 后才出现，避免快速响应时闪一下；超过 5 秒没有结果就升级为进度或超时提示加重试。

**放哪**，按离用户的视线由近到远，能近就不远：

1. **原位：** 在被操作的元素上直接变化（按钮变成"已保存"、勾号画出来）。首选。
2. **行内：** 在相关内容旁边（字段下方的错误提示、列表项旁的状态）。
3. **轻提示：** 屏幕角落短暂出现，用于看不见的结果；如果包含撤销，停留时间要够用户反应。
4. **横幅：** 影响整个页面的状态（离线、只读、服务异常），一直显示到状态解除。
5. **对话框：** 只用于必须用户做决定才能继续的情况。打断最重，最少用。

**说什么**：说结果本身，不说"成功"。"已保存，3 分钟前"比"保存成功！"有用；常规保存不需要庆祝。

## 4. 状态：先设计不顺利的情况

先设计空、出错、加载，再设计顺利的样子，顺利路径会自然好很多。只做该流程实际会遇到的状态，但每个都要想过：

| 状态 | 要设计 | 常见错误 |
| --- | --- | --- |
| 空闲 | 主操作明显 | 把空表单当空闲 |
| 加载 | 骨架和最终布局一致；按钮加载时保留文字 | 空白页正中一个转圈 |
| 空 | 为什么是空的 + 下一步做什么 | "暂无数据"，没有出路 |
| 出错 | 具体原因 + 一键恢复 + 可复制的错误编号 | "出错了"，没有重试 |
| 部分失败 | 显示成功的部分，失败的那块单独重试 | 一处失败整页空白 |
| 成功 | 简短确认 + 后续入口 | 一闪而过来不及看 |
| 冲突 | 两人同时修改时展示双方，让用户选 | 后写的悄悄覆盖前者 |
| 离线 | 告知、本地排队、恢复后同步 | 假装正常，下次同步时失败 |

空状态分三种：第一次使用（引导去创建）、筛选后为空（提示调整筛选并给清空按钮）、全部删除后（不一定需要引导）。

对话框还要处理：焦点进入、Tab 只在对话框内循环、Esc 关闭、关闭后焦点回到触发它的元素、背景滚动锁定与恢复。

## 5. 导航：我在哪、能去哪、怎么回去

- **我在哪：** 当前位置始终清楚（选中的导航项、页面标题、面包屑）。
- **能去哪：** 主要入口一直看得见；分类用用户的话命名，彼此不重叠。
- **怎么回去：** 返回总是可用，返回后恢复原来的滚动位置、筛选和输入。
- 链接打开新页面或外部网站时要看得出来。
- 搜索结果、筛选状态反映在地址里，可以分享和刷新（网页）。

## 6. 表单

**布局**
- 单列，标签在输入框上方；短而成对的字段（有效期与安全码）可以并排。
- 提示在输入框上方（打字时要看），错误在下方。
- 字段宽度暗示内容长度：邮编短，地址长。
- 选项 2–5 个用单选或分段控件；6–10 个视空间而定；超过 10 个用可搜索的下拉。
- 复选框在提交时生效，开关立即生效，别混用。
- 必填与选填要让人一眼分清，不靠开头一段说明。星号用中性色，红色只留给错误。

**校验时机**

| 时机 | 适合 | 不适合 |
| --- | --- | --- |
| 离开字段时 | 有格式的字段（邮箱、手机号、网址） | 只是必填检查 |
| 提交时 | 必填、字段之间的关系、服务器端的唯一性 | 本可以更早发现的格式问题 |
| 输入时 | 密码强度、字数统计、用户名是否可用 | 邮箱格式等大多数字段（太吵） |
| 刚打开时 | 永远不要 | — |

- 输入时校验等用户停顿 300ms 再显示，避免闪烁。
- 提交时一次列出所有问题，滚动并聚焦到第一个。
- 用户改了字段才清除它的错误。
- 出错时保留所有正确的输入，绝不清空整个表单。

**其他**
- 不要只用占位文字当标签（一输入就消失）。
- 不要禁用提交按钮却不说缺什么；更好的做法是按钮始终可点，点了再指出问题。
- 不要阻止粘贴。
- 手机上输入框文字至少 16px，否则 iOS 会自动放大页面；不要用禁止缩放来"修"。
- 超过 30 秒才能填完的表单自动保存草稿（停顿 1–2 秒后保存），显示"已保存"和时间，不用转圈。
- 多步表单：开始前说清有几步、大概多久、需要准备什么；从易到难排；可以返回且不丢内容；最后一步前给汇总页；中途离开回来能继续。

## 7. 出错、确认与撤销

**优先撤销，其次确认。** 能撤销的操作直接执行，然后给撤销（"已删除 3 个文件 · 撤销"）。确认对话框用多了，用户会习惯性点"确定"，真正危险时反而失效。

**必须确认的：** 不可逆、影响他人、花钱的操作。确认要：
- 说出具体对象和后果："删除「春季海报」？删除后无法恢复。"而不是"确定吗？"
- 按钮写动作："删除海报"和"取消"，而不是"是"和"否"。
- 危险按钮不做成最醒目的主按钮样式。
- 不可逆的大删除（账号、整个项目）让用户输入名称确认。

**乐观更新：** 点赞、开关、改小字段这类低风险操作，先显示成功，后台失败时明确回滚并给撤销或重试，不悄悄恢复。付款、删除等高风险操作必须等服务器确认。

**防止重复提交：** 提交中按钮显示"正在提交"，不能再次触发。

## 8. 文案

**错误信息三段式：** 发生了什么 + 为什么 + 怎么办。
- "上传失败。文件 62MB，上限是 50MB。可以压缩后再试。"
- "连不上服务器，你的网络似乎断开了。恢复后会自动重试。"

**按钮写动作的结果：** "保存草稿""周二发送""导出 PNG"，而不是"确定""提交""了解更多"。

**规则：**
- 同一个东西全产品只用一个叫法。
- 不责怪用户，网络问题不说"你的操作有误"。
- 错误里不开玩笑，不用感叹号；常规保存不庆祝。
- 说明为什么要某项信息（"用于找回密码"）。
- 加载超过几秒，说清在做什么、大概要多久。
- 中文界面不中英夹杂专业术语，除非用户群本来就这么说。

## 9. 不许做的设计（暗黑模式）

这些不是风格选择，是欺骗用户：
- 用羞辱的话拒绝："不了，我不在乎安全"
- 虚假的紧迫和稀缺："只剩 2 个名额"永远是 2 个
- 注册容易、注销困难
- 默认勾选营销订阅
- 先报低价，最后才出现附加费用
- 把广告伪装成内容，把"关闭"按钮藏起来

## 10. 可用性原则与设计定律的边界

**Nielsen 十大可用性原则**（评审时逐条过）：
1. 系统状态可见：操作后立即反馈。
2. 与真实世界相符：用用户熟悉的语言和顺序。
3. 用户掌控与自由：可以撤销、返回、退出。
4. 一致性与标准：同样的东西同样的样子和叫法；遵守平台惯例。
5. 防错：比事后报错更好的是让错误发生不了。
6. 辨识优于回忆：选项摆出来，不逼用户记住上一页。
7. 灵活高效：给熟手快捷方式，不妨碍新手。
8. 美观与极简：每多一条无关信息，相关信息就弱一分。
9. 帮用户识别、诊断并从错误中恢复。
10. 帮助与文档：最好不需要，需要时好找、聚焦任务。

**设计定律的正确用法：**

| 定律 | 常见误用 | 正确用法 |
| --- | --- | --- |
| Fitts 定律 | — | 高频主操作做大、放在手和指针容易到的位置；危险操作远离高频操作 |
| Hick 定律 | "导航项越少越好" | 针对同等可能的选项；分组、默认值、逐层展开同样能减少决策时间 |
| Miller 定律（7±2） | 给菜单设条数上限 | 指短时记忆，用来支持"分块"；后来的研究认为容量更接近 4 个组块 |
| F 型阅读 | 刻意按 F 形排版 | 那是结构糟糕的页面上观察到的现象；靠清晰标题、分块、关键词前置来引导 |
| 格式塔 | — | 用间距和对齐分组，比加边框更轻 |

这些是判断框架，不能代替用户研究。

## 11. 可访问性

- 键盘能完成所有主任务；焦点始终清楚可见。
- 正文对比度至少 4.5:1，大字和界面组件至少 3:1。
- 控件有可读出的名称；表单字段有关联的标签和可理解的错误提示。
- 不只靠颜色传达信息，配合文字或图标。
- 尊重"减少动态效果"设置。
- 触控目标够大、间距够开。
- 放大到 200% 内容不丢失；手机上不禁止缩放。
- 动态出现的内容（错误汇总、流式输出）对读屏软件可感知。

这些都要实际操作检查，读代码不能算通过。

## 12. 怎么知道 UX 好不好

- **任务走查：** 选 3–5 个最重要的任务，从真实入口走到完成，记录卡住、犹豫、走错的地方。
- **不顺利路径走查：** 断网、输错、空数据、中途离开再回来，各走一遍。
- **找真人试：** 少量目标用户（5 人左右）就能发现大部分严重问题；只观察，不引导。
- **能量化时看三个数：** 任务完成率、完成时间、出错次数。
- **诚实标注：** 没有真实用户参与就写"专家走查"，不写"已通过用户测试"。

## 13. 交付前自检

- [ ] 主任务的流程写下来了吗？每一步都问过"能不能省"吗？
- [ ] 每个主要操作走完了发现、操作、进行中、结果、下一步五步？
- [ ] 0.1 秒内有按下反馈？超过 1 秒有加载状态？超过 10 秒有进度和取消？
- [ ] 反馈尽量放在原位？没有滥用对话框？
- [ ] 第 4 节中实际会遇到的状态都设计了？
- [ ] 能撤销的都给了撤销？必须确认的都说清了对象和后果？
- [ ] 表单：校验时机对、出错不清空、提示与错误位置对？
- [ ] 错误信息有原因和出路？按钮写的是动作？叫法全产品一致？
- [ ] 没有任何暗黑模式？
- [ ] 键盘可完成、焦点可见、对比度够、不只靠颜色？
