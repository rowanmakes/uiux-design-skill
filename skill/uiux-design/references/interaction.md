# 交互与状态

只写模型容易漏、或测试里真出过问题的部分；通用的可用性原则、可访问性细则交给第 8 步的 impeccable `audit`。

## 1. 每个主要操作走完闭环

| 阶段 | 用户想知道 | 界面要给 |
| --- | --- | --- |
| 操作 | 我按到了吗？ | 0.1 秒内有变化（按下态、选中态） |
| 进行中 | 它在处理吗？ | 超过 1 秒显示加载；超过 10 秒给进度、能取消 |
| 结果 | 成功了吗？ | 结果本身出现在眼前；看不见的结果（复制、后台保存）用一句话说出结果 |
| 下一步 | 做错了怎么办？ | 下一步入口；能撤销的给撤销 |

**界面上显示的状态必须和数据一致。** 显示"已保存"就要真的保存了；原型里模拟的，在交付说明里写清楚。第一轮工作台测试里，动作反馈和数据对不上是共同问题。

反馈能放原位就不放远处：原位变化 → 字段旁 → 角落轻提示 → 横幅 → 对话框（最重，只在必须决定时用）。

## 2. 实际会遇到的状态都要做

| 状态 | 要设计 | 常见错误 |
| --- | --- | --- |
| 加载 | 骨架和最终布局一致 | 空白页正中一个转圈 |
| 空 | 为什么空 + 下一步 | "暂无数据"，没有出路 |
| 出错 | 具体原因 + 一键恢复 | "出错了"，没有重试 |
| 部分失败 | 显示成功的部分，失败的单独重试 | 一处失败整页空白 |
| 离线 | 告知、本地排队、恢复后同步 | 假装正常 |

出错时保留用户已填的所有内容。错误文案写"发生了什么 + 怎么办"；按钮写动作的结果（"保存草稿""导出 PNG"），不写"确定"。

## 3. 订单、结账与定价

做订单页、结账、定价页时逐条过，只做产品实际需要的项。

**结账**
- 订单内容全程可见：买了什么、多少、规格。
- 付款前显示完整总价，运费、税、优惠都算进去，不在最后一步冒出新费用。
- 多步时有带名称的步骤进度（"第 2 步，共 3 步：配送"）；付款前有核对步骤，每部分能回去改。
- 允许游客结账；必须注册时说明为什么。
- 提交后等服务器确认才显示成功，期间按钮显示"正在提交"且不能重复点；付款不做乐观更新。
- 付款失败时保留购物车和已填内容，说清原因（卡被拒、网络问题），给下一步。

**订阅**
- 写清扣费周期、下次扣费日期、怎么暂停和取消；取消和订阅一样容易找到。
- 配送节奏和计费口径分开写，不能互相矛盾。

**定价**
- 写清按什么计（每袋、每月）、什么币种、含不含税；方案之间一眼能比，推荐的只有一个。

**不许做：** 虚假的紧迫和稀缺、默认勾选营销订阅、先报低价最后才出附加费、注册容易注销困难、用羞辱的话拒绝。
