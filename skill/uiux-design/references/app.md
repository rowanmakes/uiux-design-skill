# 手机 App 与桌面客户端

适用：跨平台手机 App（Flutter、React Native 一类，一套代码跑 iOS 和 Android）和桌面套壳客户端（Electron、Tauri 一类）。

`taste.md` 里的决定方式在这里同样成立（一个主角、一个强调色、低饱和、精确对齐、真实数据、中文排印），但它的网页参数不能直接套：营销页的大留白、首屏骨架和滚动叙事，到了 App 里大多不适用。本文件覆盖这些差异。

## 1. 核心原则：平台规范先于创意

网页可以自由构图，App 不行。用户在每个平台上已经形成了肌肉记忆：底部标签栏在哪、怎么返回、弹层从哪出来、快捷键是什么。为了"不一样"去破坏这些，用户感到的是别扭，不是惊艳。

**惊艳建立在规范之上，不是代替规范。** 先把导航、返回、弹层、菜单这些地方做得和平台一样顺，再在内容、质感和手感上做出自己的样子。

App 是每天反复用的工具，音量接近 `SKILL.md` 里的"操作型"页面：低而稳。品牌表达集中在少数时刻，不铺满每一屏。

## 2. App 的惊艳从哪来

网页的惊艳靠首屏构图和视觉冲击；App 的惊艳主要靠四件事：

1. **手感。** 跟手的手势、有重量的弹簧、按下立刻有回应。用户拖动一张卡片时它就在手指下面，松手后按惯性落到该去的地方。
2. **连续。** 点的东西就是下一屏的主角：列表里的一项放大成详情，返回时缩回原位。用户始终知道自己从哪来、在哪。
3. **一处做到 120%。** 一个签名交互或一个关键时刻做到极致，其余做到 80% 的干净可靠。到处平均用力，结果处处平淡。
4. **状态完整。** 空、加载、离线、失败、权限，每个状态都想好了。高级感很大一部分来自"没有一处是没想过的"。

签名交互从产品里找：这个产品里的哪样东西，因为用户的哪个动作，发生了只有它才会有的变化。找不到就把基本动效做准，不硬造。

## 3. 五个词在 App 里的参数

数值是起点，平台规范和真实内容优先。

| 词 | 手机 | 桌面客户端 |
| --- | --- | --- |
| **留白** | 不靠大段空白，靠节奏：屏幕左右边距 16–20pt；组内 8–12，组间 24–32；内容铺满，减少一层容器 | 侧栏与内容之间、内容区内边距要稳；密度可以比手机高，但每个区域有明确的呼吸 |
| **干净** | 少一层卡片、少一条分隔线、少一个装饰性图标；一个强调色只给当前选中和主操作 | 同左；边框极淡，层级靠背景明度区分；优先用系统材质而不是自己画渐变 |
| **简约** | 每屏一个主任务；底部标签 3–5 个；次要操作收进菜单或长按 | 主窗口一个主区域；次要信息放检查器或按需展开；所有命令都能在菜单或命令面板里找到 |
| **大气** | 大标题（如 iOS 大标题样式）、满屏的主内容（照片、作品、数据图）、尺度反差 | 主内容区够大；一个视图里只有一个视觉重心 |
| **干练** | 文案短，按钮写具体动作；动效短而跟手；一步能完成的事不拆两步 | 键盘优先：常用操作有快捷键，命令面板可达；反馈即时 |

字号起点：手机正文中文 15–17，英文 17pt / 16sp；最小标签不低于 12；桌面工具正文 13–14px，阅读内容 15–16px。都要支持系统字号放大，不能固定死。

## 4. 手机端

**导航与结构**
- 顶层分区用底部标签栏，3–5 个，始终可见；不要用汉堡菜单藏主要分区。
- 临时任务用底部弹层，内容可以拖动关闭；复杂任务用全屏页面。
- 返回：iOS 从左边缘滑动返回，Android 系统返回手势和返回键。自定义转场不能挡住这些手势。
- 屏幕宽度变化时（大屏手机、平板、折叠屏）按可用宽度布局，不按设备型号写死。

**单手与触控**
- 触控目标 iOS 至少 44×44pt，Android 至少 48×48dp；相邻目标留间隔。
- 主操作放在拇指容易够到的下半屏；危险操作远离高频操作。
- 键盘弹出时输入框不能被挡住。

**安全区**
- 内容不能被刘海、灵动岛、状态栏、底部手势条挡住；背景可以铺进安全区，可点的东西不行。

**触感反馈**
- 选中、完成、出错可以配轻微的系统触感；只用在有意义的时刻，频繁震动比没有更糟。

**深浅色**
- 两套都要设计，不是把浅色反色。深色底用带一点色温的近黑，层级越高越亮。

## 5. 桌面客户端

套壳客户端最常见的失败是"一看就是网页"：没有原生菜单、快捷键不通、右键弹出浏览器菜单、窗口控件位置不对。

- **菜单：** 原生菜单栏包含所有命令，标准快捷键都能用（复制、粘贴、撤销、设置、关闭窗口）。macOS 上设置放在应用菜单里。
- **窗口：** 窗口控件跟随系统（macOS 在左上、Windows 在右上）；可调大小，有合理的最小尺寸；需要时支持多窗口。自定义标题栏时保留拖动区域和双击行为。
- **键盘：** 命令面板（类似 Linear、Raycast）让所有操作可搜索可达；焦点清楚可见；Tab 顺序合理。
- **指针：** 悬停有反馈；右键菜单是应用自己的，内容和当前对象相关。
- **材质：** 优先用系统真实的材质（macOS 的半透明、Windows 11 的 Mica / Acrylic），不要用网页模仿一层毛玻璃。
- **布局：** 常见结构是侧栏 + 内容 + 可选的检查器；随窗口宽度收起侧栏或检查器。
- **性能感：** 启动先显示骨架而不是白屏；长任务在原地显示进度，不阻塞整个窗口。

## 6. 动效与手感

App 的动效是交互的一部分，不是装饰。

**每个界面先做三处：**
1. 主操作的反馈：按下立即有回应（约 80ms 内），完成时交出结果。
2. 一处状态切换的来路：东西从哪里来、到哪里去看得见。
3. 第一次进入时的一次出场：主角先到，其余跟上，只播一次。

**手感用"动作 + 实物"来定，再换算成弹簧参数**（刚度 / 阻尼，具体数值要按所用动画库的定义换算）：

| 动作 | 实物参照 | 起点参数 | 适合 |
| --- | --- | --- | --- |
| 咔嗒 | 磁铁吸合、卡扣 | 350–400 / 10–15 | 按钮、开关、展开 |
| 滑入 | 抽屉阻尼 | 250–300 / 20–25 | 底部弹层、侧栏 |
| 流淌 | 倒蜂蜜 | 150–200 / 30–40 | 页面转场、主视觉出现 |
| 砸落 | 重物落桌 | 400–500 / 5–10 | 确认、完成 |

高频操作用短促的动作；品牌时刻才用绵长的。大面积的东西（整页、面板）几乎不过冲，小东西（勾选、徽章）可以有弹性。

**规则：**
- 跟手：拖动、滑动时动画进度直接跟着手指走，松手后按速度继续，不跳回起点重播。
- 可打断：动画进行中再次操作，从当前位置接着走。
- 连续：列表进详情用共享元素放大，返回时缩回原位并恢复滚动位置。
- 方向一致：打开和关闭互为逆过程；同一次切换里所有东西朝一个方向。
- 离开比进入快：退出约为进入时长的 60–75%。
- 业务状态立即更新，不等动画结束。
- 系统开启"减少动态效果"时，状态直接到位，内容一样不少。

**时长起点：** 按下与选中 150–300ms；弹层与侧栏 250–400ms；整页切换 350–500ms，超过 500ms 就让人等；首次出场每项间隔 40–80ms，总长不超过 600ms。

## 7. 状态清单

App 比网页多出很多状态。只做产品实际会遇到的，但这些都要过一遍：

- 首次启动与引导（能跳过）、空状态（说明下一步做什么）
- 加载（骨架与最终布局一致）、下拉刷新、分页加载
- 离线与弱网（已有内容仍可看，操作排队或明确失败）
- 失败（说清原因，可重试，保留用户输入）
- 权限请求（先说明为什么需要，再请求；被拒后有替代路径）
- 推送与通知（点进来落到对应内容）
- 深浅色、系统字号放大、横竖屏（如支持）
- 后台返回后的状态恢复

## 8. 跨平台的取舍

一套代码跑 iOS 和 Android 时，逐个组件决定：跟随各自平台，还是用一套共享设计，并写下来。

- **用户最敏感、建议跟随平台的：** 返回方式、底部弹层的行为、系统级控件（日期选择、分享、权限弹窗）、字体回退、触感。
- **可以统一成自己设计的：** 品牌色、内容卡片、插画和图标风格、签名交互、数据可视化。

桌面同理：Windows 和 macOS 在窗口控件、快捷键修饰键（Ctrl / Cmd）、菜单位置、设置入口上跟随系统，内容区统一。

## 9. 实现提示（按技术栈）

下面是设计概念到框架的对照，具体 API 以所用版本的官方文档为准。

| 设计需要 | Flutter | React Native | Electron / Tauri |
| --- | --- | --- | --- |
| 安全区 | `SafeArea` | 安全区库（如 react-native-safe-area-context） | 标题栏与窗口边框的避让 |
| 系统字号 | `MediaQuery` 的文字缩放 | 字体缩放设置 | 跟随系统缩放，用相对单位 |
| 弹簧与手势 | 物理模拟动画、手势识别 | 常用 Reanimated + Gesture Handler | CSS / Web Animations，或动画库 |
| 共享元素转场 | `Hero` | 动画库的共享过渡 | 视图过渡 API 或自写 |
| 毛玻璃 | `BackdropFilter` | 模糊视图组件 | 优先系统材质（macOS 半透明、Windows Mica），其次 `backdrop-filter` |
| 原生菜单 | — | — | 框架的菜单 API；所有命令进菜单 |

## 10. 原型与验证

设计判断先用 HTML 原型验证，最便宜；设计定下来再按技术栈实现。

**手机原型：**
- 平铺 4–6 个主界面，每台都能点（切换标签、打开弹层），不是静态摆拍。
- 展示板要有构图：最能代表产品的那一屏放大放在中心，其余错落围绕；或按任务流程串起来；或旁边放一个签名交互的局部特写。一排等大的手机看起来像表格。
- 设备外框用现成的标准组件，不手写状态栏和灵动岛，手写几乎必然位置出错。
- 截图视口用手机尺寸（如 390×844），并在深色模式下各截一次。

**桌面原型：**
- 至少两个窗口宽度：常用尺寸（如 1280×800）和最小窗口尺寸。
- 把菜单、快捷键、右键菜单写进设计说明，原型里能演示的就演示。

**必须实际操作的：** 手势、转场、可打断性、键盘操作，截图证明不了，要点过、拖过才能说验证过。

## 11. 交付前自检

- [ ] 返回、弹层、标签栏、菜单、快捷键是否和平台一样顺？
- [ ] 触控目标够大，主操作在拇指区？
- [ ] 安全区：没有可点的东西被挡住？
- [ ] 一处签名交互做到位了吗？说得出它来自产品的什么吗？
- [ ] 列表进详情、返回，是否连续且恢复位置？
- [ ] 第 7 节的状态都过了一遍？
- [ ] 深色模式和系统字号放大都检查过？
- [ ] 桌面：原生菜单、快捷键、右键菜单、窗口控件、系统材质？
- [ ] 换名字测试：换成同类产品的名字，几乎不用改吗？
