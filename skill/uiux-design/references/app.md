# 手机 App 与桌面客户端

适用：跨平台手机 App（Flutter、React Native 一类）和桌面套壳客户端（Electron、Tauri 一类），这是用户自己产品用的技术路线。专业工具的桌面端看 `workbench.md`。

**尚未测试。** 本文件只留和网页做法冲突、容易做错的部分；平台的通用规范（触控尺寸、安全区、导航模式）请按所用平台的官方指南来。

## 1. 平台规范先于创意

用户在每个平台上有肌肉记忆：底部标签栏在哪、怎么返回、弹层从哪出来、快捷键是什么。为了"不一样"去破坏这些，用户感到的是别扭，不是惊艳。先把导航、返回、弹层、菜单做得和平台一样顺，再在内容、质感和手感上做出自己的样子。

官网那套大留白、首屏骨架、滚动叙事，到了 App 里大多不适用。App 是每天反复用的工具，音量低而稳，品牌表达集中在少数时刻。

## 2. App 的惊艳从哪来

1. **手感：** 跟手、可打断。拖动时东西就在手指下面，松手按速度继续；动画进行中再次操作，从当前位置接着走。
2. **连续：** 点的东西就是下一屏的主角。列表里的一项放大成详情，返回时缩回原位并恢复滚动位置。
3. **一处做到极致：** 一个签名交互做到 120%，其余做到干净可靠。签名交互要说得出来自产品的什么，找不到就把基本动效做准，不硬造。
4. **状态完整：** 空、加载、离线、失败、权限被拒，都想过。

开启"减少动态效果"时，状态直接到位，内容一样不少。

## 3. 跨平台的取舍

一套代码跑 iOS 和 Android 时，逐个组件决定跟随平台还是用共享设计，并写进 DESIGN.md：
- **跟随平台：** 返回方式、底部弹层的行为、系统控件（日期、分享、权限弹窗）、字体回退、触感。
- **可以统一：** 品牌色、内容卡片、图标风格、签名交互、数据可视化。

桌面上 Windows 和 macOS 的窗口控件、快捷键修饰键（Ctrl / Cmd）、菜单位置跟随系统，内容区统一。套壳客户端的约定见 `workbench.md` 第 5 节。

## 4. 原型与验证

设计判断先用 HTML 原型验证，定下来再按技术栈实现；动效参考的实现方式也按技术栈来（Flutter、React Native、Electron、Tauri 各用自己的动画能力）。
- **手机：** 视口 390×844，浅色、深色各截一次；平铺 4–6 个主界面，每个都能点；设备外框用现成组件，不手写状态栏和灵动岛。
- **桌面：** 常用尺寸（如 1280×800）和最小窗口尺寸各一次；菜单、快捷键、右键菜单写进设计说明。
- 手势、转场、可打断性要实际点过、拖过，截图证明不了。
