# 基础：这个项目的来龙去脉

整理自用户与 Claude 的对话（2026-10-16 笔记至 2026-10-28）。以后改 Skill 之前先读这份：它记录用户说过什么、定过什么、为什么现在是这个样子。按奥卡姆剃刀原则，"用户说的"是 Skill 内容的四种出处之一，出处就从这里查。

品牌设计是另一个方向，在 [brand-skill](https://github.com/rowanmakes/brand-skill) 仓库，本文件不涉及。

## 1. 目标

- 做一个属于用户自己的 UI/UX 设计 Skill：从产品描述出发，做出**惊艳**、可落地的界面，不要平平无奇、千篇一律的 AI 模板。
- 起点是用户 2026-10-16 的研究笔记（`docs/research/2026-10-16-original-notes.md`）。ComfyArt 只是参考和测试对象，把一个站做好不算验证了设计能力。
- 要覆盖：官网和落地页、同品牌的产品页与订单页、桌面工作台、手机 App 与桌面客户端、AI 界面。用户自己的产品是跨平台手机端（Flutter 或 React Native）加桌面套壳（Electron 或 Tauri），带工作台和 AI 生图。

## 2. 用户的品味（用户原话或确认过的）

- **五个词：** 留白、干净、简约、大气、干练。
- **喜欢：** Linear（极客）、苹果（简约克制）、Spaceship（spaceship.com，动效）、Cursor 官网、Grok（高级）、Dishoom、Awwwards 获奖作品。
- **无感：** Stripe Press（动效好但感受不出什么）、The Pudding、Teenage Engineering（巨物感，不高级）。
- **分页面类型（2026-10-21）：**
  - 官网要**电影感**：有来源的光、有空气、像一个场景。氛围试样板里选了雾中山、余烬、胶片；没选白昼、留白、缺席。
  - 工作台要**极客风**：精确、快、键盘优先。两者不混用。
  - 产品页、订单页要延续官网的切换动效和质感，音量降低。
- **不要千篇一律：** 不能所有官网都是一个样子；形式本身也会审美疲劳。
- **动效：** 帮用户理解页面或突出重要内容，不需要每个区块都动，宁可少用。Magic UI 只当参考，实现按实际技术栈来。
- **不想自己找感觉：** 找参考、挑字体像大海捞针，要 agent 来挑，用户只做判断。

## 3. 用户定下的做法

| 日期 | 决定 |
| --- | --- |
| 10-21 | 先问清楚，再找同类产品和参考 |
| 10-21 | 参考来源：作品集看 Minimal Gallery，落地页看 Land-book，产品界面和流程看 Mobbin，最常用 getdesign.md，最后才用 Pinterest |
| 10-21 | DESIGN.md 从 awesome-design-md 的种子起步，写气质、色彩、字体、留白、动效档位、不适合我们的设计 |
| 10-21 | 用户确认三件事：整体感觉对不对、有没有漏掉喜欢的、有没有加入不喜欢的 |
| 10-21 | 最后打开网址对照 DESIGN.md 检查视觉层级、间距、移动端、一致性，再用 taste-skill 和 impeccable 检查 |
| 10-22 | 用户问参考是否每次都要保存；建议是项目内全留、只把用户有反应的收进 `library/`（用户未明确拍板） |
| 10-24 | 用**奥卡姆剃刀**优化：每一节必须有出处，没有就删；消融只用于拿不准的几项 |
| 10-25 | 字体采用 Anthropic frontend-design 的做法，**不建字体库、不获取别人的字体文件**，只用公开字体服务或已授权的字体 |

## 4. 测试证明了什么

| 实验 | 结果 | 结论 |
| --- | --- | --- |
| 第一轮（10-21） | 无技能 / frontend-design / 我们三组都千篇一律；我们的工作台没交付 | 规则只能推到"不错"，推不到"惊艳"；工作台读的文件太多可能是原因 |
| E1 | 先出三个方向能跳出默认外观，但 agent 自己挑选错了方向；用户：还是一般 | 方向交给用户挑 |
| 氛围试样板 | 用户几分钟就选出电影感 | 用"看"代替"问" |
| E2 | 生成的场景图加滚动叙事，用户："确实可以" | 唯一的正面证据；生图是关键；三页已有趋同苗头 |

详细记录在 `docs/tests/`，复盘在 `docs/retro-2026-10-21.md`，覆盖情况在 `docs/coverage.md`。

## 5. 工作原则

- 先测试，再加规则；测试结果出来之前不扩充 Skill。
- 奥卡姆剃刀：每节内容要有出处（用户说的、测试证明的、防过真实失败的、脚本在执行的），见 `docs/ablation-plan.md`。
- 用户是裁判；评审 agent 的分数只作参考。
- 反复出现的问题做成检查脚本（`design_lint.py`、`honesty_check.py`），不再写一句"注意"。
- 诚实：不编造客户、评价、数据；生成图不称实景；运行日志如实写。

| 模型 | 用户的额度 | 负责 |

| Claude（$20 档） | 少 | 改 Skill、设计实验、看结果做决定 |

规则：建页和评审不是同一家；一次实验只换一个变量；贵的模型不做重复劳动。Orca 只是调用方式。Kimi 是否续费，看用户在本项目以外用得多不多。

## 7. 基础设施讨论（10-22，尚未定，未部署）

- **云端的限制：** Claude 的云端只能访问白名单网站（GitHub、npm 等），连不上用户的 VPS；密钥不要贴进对话。
- **"发消息就回"的方案：** 在美国 VPS 上部署一个 MCP 服务，加成 Claude 的自定义连接器，只开放"发消息、开任务、查任务、取文件"。长任务开了就返回编号、分次查进度。用户说"先不用写，先讨论清楚"。待确认：账号能否加自定义连接器、OMP 能否非交互运行。
- **协调方式：** 倾向 VPS 上的 agent 常驻做日常执行，Claude 负责方案、评审和改 Skill。
- **统一存储：** 用户想统一管理、文件都有链接。建议 RustFS（有网页控制台、Apache-2.0），备选 Garage；MinIO 社区版已归档停更。
- **备份：** 用户在世界各地都有 VPS。建议主存储在美国，用 restic 每天备份到另外两个地区，备份机设成只能追加、不能删除，每月做一次恢复演练。
- **公网：** 走 Cloudflare Tunnel，不开端口、不暴露 IP；控制台加 Cloudflare Access；注意单次上传 100 MB、请求约 100 秒的上限。也可以考虑 Cloudflare R2。
- **前提：** 仓库改成私有（目前两个仓库都是公开的）。
