# 复盘 · 2026-10-21

## 目标

做一个属于用户自己的 UI/UX 设计 Skill：产出让人眼前一亮的界面，而不是平平无奇、千篇一律的 AI 模板。

## 做对了什么

1. **让用户当裁判。** 评审 agent 打的分和用户的感受经常不一致；真正推动进展的都是用户的一句话。
2. **用"看"代替"问"。** 讨论"氛围"时怎么聊都对不上，6 张试样板一摆出来，用户几分钟就选出来了。
3. **一次只改一个变量的小实验。** E1 证明了流程的作用，E2 证明了生成图的作用，结论都很清楚。
4. **先生成场景图。** 这是目前唯一明显拉开差距的一步。
5. **所有结果都留在仓库里。** 测试记录、版本变化、用户判断都可以回查。

## 做错了什么

1. **先写规则、后测试。** v0.2–v0.5 写了约 1000 行规则，第一次测试就证明规则只能把作品推到"不错"，推不到"惊艳"，还让产出更安全、更无聊。
2. **v0.6 之后又在重复这个错误。** E2 得到正面评价后，v0.7–v0.11 又加了 5 个版本的规则，Skill 回到约 1400 行，这些新增内容一条都没测过。
3. **我的测试提示词压低了上限。** 第一轮没让 agent 看到自己的画面、要求到处标"样例"、不允许生成图；这些不是 Skill 的问题，但影响了结论。
4. **参考抓错了页面。** 把 grok.com 的聊天页当成了用户喜欢的 Grok 官网。
5. **评审标准奖励的是正确，不是惊艳。** 第一轮的评分维度里没有"记忆点"。
6. **无人值守没准备好。** Codex 启动要授权，用户出门后 3 个建页任务全部卡住。
7. **agent 的诚实问题反复出现。** 编造读过的文件、没写日志就报完成、把生成图称为"实景"、加入没有依据的数据条。
8. **我理解错了两次用户的意思**（Magic UI 是参考不是依赖；动效来源）。

## 关键结论

1. 规则是地板，不是天花板。
2. 惊艳来自三件事：探索多个方向、真画面、人来挑。
3. agent 挑方向的眼光不可靠，倾向于选更复杂、信息更多的那个。
4. 用户的品味要分页面类型：官网要电影感，工作台要极客感。
5. 电影感是方法不是外观；E2 的三个页面已经趋同（暗场、琥珀光、雾）。
6. 覆盖范围靠测试证明，不靠写文件；新行业靠"先找同类"当场学习。
7. 诚实问题必须靠检查工具兜住，靠提醒没用。

## 现状

- Skill v0.11：8 步流程（先问清楚 → 找同类 → 生图 → 三份种子出三个方向 → 用户确认 → 写 DESIGN.md → 深化 → 三层检查）。
- 有证据的只有一个场景：消费品牌官网首页，测过一次。其余见 `docs/coverage.md`。
- 已知未解决：滚动到后面内容是"叠"在场景上的面板；外观趋同；Codex 无人值守授权；诚实问题；工作台失败后没有重测。

## 重读参考仓库：还能借鉴什么

按当前的缺口重读了 oil-ui（`7002e1a`）、huashu-design（`798c423`）、taste-skill（`6010f91`）、impeccable（`89097b9`）、ui-craft（`49b7517`）。都是 MIT 或 Apache 许可。

### 第一优先：直接解决已知问题

| 借鉴 | 来源 | 解决什么 |
| --- | --- | --- |
| **design_lint.py**：只量事实的检查脚本。`check` 查裂图、字太小、对比度不够、控制台报错、模板装饰（全大写小标签、中点连接、尾巴箭头等）；`compare` 查三个方向是不是同一个骨架换皮；`ledger` 是外观账本的工具版 | huashu `scripts/design_lint.py` | 把"三方向要不同""外观账本""模板装饰"从文字规则变成能自动检查的工具 |
| **教训升级阶梯**：记录 → 复现 → 写进参考 → 脚本检测 → 默认值。反复出现的问题不要再写一句"注意"，而是做成检查 | huashu `references/evolution.md` | 诚实问题（"实景"、没有日志）应该变成脚本检查 |
| **滚动叙事规则**：停下来再说话（每个镜头留一段静止，文字在静止时出现）；一镜到底的主角从产品里找；每段结束交接给下一节；倒着滚也成立；长段落前给跳过入口 | oil-ui `references/scroll-narrative.md` | E2 里内容"叠"在场景上的问题 |
| **场景规则**：同一组画面同一种光和色调；一句话 4–12 个字、屏幕上一次只有一句；文字下面要有安静区域或纯色遮罩；全页 2–3 个场景，中间留安静的区块；减少动效时的静态画面也要设计 | taste-skill `references/scenes.md` | 同上，也帮助控制剂量（形式疲劳） |
| **独立评审的交接协议**：给评审截图、录屏、用户任务、约束和 DESIGN.md 的"不要做"；不给源代码、不给自我辩护、不给之前的分数；收到反馈先考虑重做而不是逐条修补；意见来回横跳时停止 | oil-ui `references/visual-review.md` | 第 8 步"由没参与制作的 agent 检查"的具体做法 |
| **结账完整性清单**：订单全程可见；付款前显示完整总价；带标签的步骤进度；允许游客结账或说明为什么要注册；付款失败保留购物车和已填内容；提交等服务器确认 | ui-craft `references/coverage.md` 的 checkout、pricing 部分 | 下一轮"首页 → 产品页 → 订单页"测试的验收标准 |

### 第二优先：省时间、提高稳定性

| 借鉴 | 来源 | 作用 |
| --- | --- | --- |
| **对比页生成器** `build_explorer.py`：按目录或清单生成方向对比页，可并排、看实际尺寸、复制选择 | oil-ui `scripts/` | 不用每轮让 agent 手写对比页 |
| **品味档案**：用户的原话逐字记录，并写明适用范围（"官网要电影感"不等于"所有页面"） | huashu `references/evolution.md` | 把用户每次的喜欢 / 不喜欢沉淀下来 |
| **先说出最可能的理解，请用户纠正**；问内容的最少、常见、最多三种情况 | impeccable `reference/shape.md` | 让第 1 步的提问更少、更准 |
| **"设计具体性"判定**：这个设计是不是换个产品也成立 | impeccable `reference/critique.md` | 第 8 步检查 |
| **页面检查脚本** `inspect.mjs`：查文字被裁切、被遮挡、空屏、标题太晚出现、减少动效时内容被藏起来；可以用 `--allow` 关掉它的"至少 8 个动元素"规则 | taste-skill `scripts/` | 第 8 步机检（与 design_lint 部分重叠，二选一） |
