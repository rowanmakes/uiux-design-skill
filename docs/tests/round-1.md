## 观察到的现象

1. **07-C 在 30 分钟内没有交付任何东西**，也没有 run-log。原因未知；同一简报 A、B 都完成了。这是本轮最严重的问题。
2. **01 三组外观高度趋同：** 都是暖纸色或浅色底、衬线大标题、顶部"样例说明"横幅、左文右卡的分栏、三格事实卡加两个按钮。C 组恰好选了暖纸色加琥珀赤褐，正是 `taste.md` 警告的默认外观；B 组的 frontend-design 明确排查了这个默认，改用冷雾青灰，评审在品牌辨识度上给了 B 更高分。
3. **C 组的交互状态最完整（4 分），但用力过度：** 把"模拟网络超时""厌氧（演示空状态）"这类测试开关放进了顾客的购买路径；加了简报没要求的收件信息表单；"已暂存草稿"只是改了文字，没有真的保存。
4. **窄屏数据表格：** A、C 的豆子对照表在手机上被挤成逐字换行；B 改成了带字段名的条目。
5. **所有组都没法截图自查：** 子 worktree 里没装 playwright，C 组 Skill 要求的视觉自检、模糊测试无法执行。
6. **"样例 / 占位"标签铺满页面**（三组都是），明显伤害观感。这部分源于测试素材和提示词要求"标注样例"，以及 Skill 的诚实规则。
7. **07 的 A、B 都只有 2.8–2.9 / 5：** 键盘可达性、小窗口布局、动作反馈与数据不一致是共同问题。

## 待验证的假设

- 07-C 失败与 Skill 太重有关：工作台简报会路由到 `taste.md`、`app.md`、`workbench.md`、`ai.md`、`interaction.md`，加上 `SKILL.md` 约 1000 行，再叠加"状态做全"的要求。需要看 07-C 子 worktree 的残留文件或会话记录确认。
- C 组的外观趋同说明 `taste.md` 列出了默认外观，但没有一个强制"先检查、再偏离"的步骤；frontend-design 有。

## 测试环境要修的（不属于 Skill 改动）

- 每个子 worktree 预装 playwright 和截图脚本，让生成者能自己看画面。
- 样例声明只放一处（页脚或交付说明），提示词不再要求逐处标注。
- 每格至少跑 2 次，才能区分 Skill 的作用和随机波动。
